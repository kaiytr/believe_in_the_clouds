# 재화 시스템 가이드 — 개발자·AI용

작성일: 2026-10-31

다른 로컬에서 이어받는 경우 [개발 인수인계](CurrencySystem_Handoff.md)의 현재 상태·이동 파일·시작 절차부터 확인한다.

**확정 범위: 재화 시스템을 테스트 씬에서 독립 검증한다. 메인 플레이 루프 연동은 나중에 진행한다. 현재는 문서만 수정하며 구현을 시작하지 않는다.**

**이 문서는 향후 구현할 API의 사용 계약이다. 현재 공통 API는 구현되지 않았다. 아래 예제를 기존 프로젝트에서 실행할 수 있다고 가정하지 않는다.**

**메인 플레이 루프도 아직 구현되지 않았다.** 로비 → 분기 선택 → 스테이지 역할 수행 → 로비 복귀 → 다음 분기 → 보스 → 엔딩은 목표 흐름이다. 실제 로비·분기·이어 하기·엔딩 연동은 후속 작업이며 이번 재화 검증에 포함하지 않는다. 테스트 어댑터가 필요한 처치·사망·장착 상태를 제공한다.

규칙의 근거는 [상세기획](CurrencySystem_Design.md), 내부 구조는 [개발명세서](CurrencySystem_TechnicalSpec.md)를 따른다. 지금은 문서 검토 단계이며 사용자 구현 지시 전에는 게임 코드를 작성하지 않는다.

현재 재화 검증 범위의 게임 규칙은 모두 확정됐다. 연출 수치는 테스트에서 조정할 초기값이며, 후속 콘텐츠 관련 결정은 나중에 진행한다.

## 1. 먼저 알아야 할 규칙

- 초기 코인 0개, 초기 교리·조각 지급 없음, 초기 장착 없음이다.
- 공통 진입점은 Currency, 자산 원장은 하나다.
- 단위는 정수 코인이다. 보유 잔액과 비행 중 대기 보상은 구분한다.
- 지급/소비에는 양의 금액과 비어 있지 않은 사유를 전달한다.
- 코인·조각·대기 보상·사망 결과는 같은 경제 거래로 저장한다.
- 사망 시 **전부 미장착 → 전체 보유 조각 목록 확정 → 그 목록 총수의 30% 버림 손실** 순서다.
- 장착 여부로 조각 손실을 분리하거나 완성 교리 개수로 별도 손실을 계산하지 않는다.
- HUD·상점·적이 잔액이나 저장 파일을 직접 수정하면 안 된다.
- 저장 실패 거래는 공개 자산에 반영하지 않는다.
- 지급 상한 때문에 실제 처리량이 요청량보다 작을 수 있으므로 결과를 확인한다.

## 2. 계획된 공통 API 빠른 참조

| 필요 | 호출 |
| --- | --- |
| 현재 사용할 수 있는 코인 | Currency.Balance |
| 아직 비행 중인 코인 | Currency.PendingBalance |
| 거래 가능 상태 | Currency.IsReady |
| 금액을 낼 수 있는지 화면에서 안내 | Currency.CanAfford(amount) |
| 연출 없이 코인 지급 | Currency.TryGrant(amount, reason, transactionId) |
| 지정 위치에서 HUD로 날아가며 지급 | Currency.TryGrantWithEffect(amount, position, reason, transactionId) |
| 코인 소비 | Currency.TrySpend(amount, reason, transactionId) |
| 잔액·대기량 변경 반영 | Currency.Changed |
| 코인 지불과 교리 획득을 함께 처리 | EconomyService.TryPurchase(request) |

특정 기능의 사유를 중앙 서비스에 새 enum이나 switch로 등록할 필요는 없다. reason은 진단 가능한 짧은 문자열을 사용한다.

## 3. 사용 예제

다음 코드는 **제안 API를 설명하는 예시**다. 최종 구현에서 이름이 달라지면 이 문서도 같이 갱신한다.

### 3.1 연출 없는 일회성 보상

```csharp
var result = Currency.TryGrant(
    amount: 50,
    reason: "quest.completed",
    transactionId: $"quest:{questInstanceId}/reward");

if (!result.Success)
{
    ShowRewardError(result.Error);
    return;
}

// 상한에 걸리면 50보다 작을 수 있다.
ShowGrantedAmount(result.AppliedAmount);
```

동일한 퀘스트 보상을 재시도할 때는 같은 transactionId를 유지한다. 버튼을 누를 때마다 새 GUID를 만들면 중복 방지가 되지 않는다.

### 3.2 적 사망 위치에서 자동 획득

```csharp
var result = Currency.TryGrantWithEffect(
    amount: rolledCoins,
    position: enemyBodyCenter,
    reason: "enemy.defeat",
    transactionId: $"stage:{stageInstanceId}/enemy:{spawnId}/defeat");
```

성공은 보상 예약과 저장 성공을 의미한다. 도착 시 추가 TryGrant를 호출하면 두 번 지급하므로 안 된다. 도착 정산은 CoinFlightView와 서비스 내부가 맡는다.

이번 테스트에서는 안정적인 테스트 문맥·처치 ID로 중복 방지를 검증한다. 위 예시의 stageInstanceId/spawnId는 향후 메인 루프에서 연결할 식별자 예다. 후속 진행 저장에서는 적 생사와 보상 예약을 같은 트랜잭션으로 묶는다. 같은 거래 ID를 다시 제출해도 드롭량을 다시 추첨하지 않는다.

### 3.3 코인만 소비하는 기능

```csharp
var result = Currency.TrySpend(
    amount: fee,
    reason: "stage.entry_fee",
    transactionId: $"stage-entry:{entryRequestId}");

if (!result.Success)
{
    ShowPaymentError(result.Error);
    return;
}

ShowPaymentComplete(result.AppliedAmount);
```

CanAfford는 안내용이다. CanAfford가 true여도 다른 거래가 먼저 발생할 수 있으므로 최종 결과는 TrySpend가 결정한다.

지불 후 별도의 아이템 생성·강화·스테이지 진입이 실패할 수 있다면 이 예제를 그대로 사용하지 않는다. 해당 결과 상태를 저장 조정기의 같은 구매/진입 트랜잭션에 포함해야 한다.

### 3.4 교리 조각 구매

상점은 선택한 **카드 ID 목록**으로 PurchaseRequest를 만들어 EconomyService.TryPurchase에 전달한다. 가격·등급은 ShopCatalog가 결정한다. UI가 합계 금액을 직접 지불하고 조각을 따로 AddEntry로 지급하지 않는다.

거래 성공 후에만 선택을 지운다. 잔액 부족과 저장 실패에서는 선택을 유지한다. 연타를 막기 위한 버튼 비활성만으로 원자성이나 중복 방지를 대신하지 않는다.

### 3.5 화면 바인딩

```csharp
void OnEnable()
{
    Currency.Changed += HandleCurrencyChanged;
    RenderBalance(Currency.Balance);
}

void OnDisable()
{
    Currency.Changed -= HandleCurrencyChanged;
}

void HandleCurrencyChanged(CurrencyChange change)
{
    RenderBalance(change.AfterBalance);
}
```

위 예제는 최소 흐름이다. 실제 화면에서는 IsReady와 오류/잠금 상태도 표시한다. 씬 이동으로 화면이 재생성되면 현재 값을 한 번 읽어 초기화한다. Changed를 받았다는 이유로 보상을 재지급하지 않는다.

## 4. 새 지급처·소비처를 추가하는 절차

1. 지급량/비용과 사유를 기능 기획에서 정한다.
2. 연출이 필요한 지급인지, 즉시 지급인지 결정한다.
3. 재시도 가능한 일회성 사건이면 안정적인 거래 ID를 정한다.
4. 단순 코인 변경이면 Currency API를 사용한다.
5. 자산이나 진행 결과가 함께 바뀌면 같은 저장 트랜잭션에 묶는다.
6. 성공 후에만 완료 UI를 표시한다. 실패 시 기존 상태를 유지한다.
7. 재시도·잔액 부족·저장 실패·중복 요청을 확인한다.

이 절차를 따르는 새 퀘스트/이벤트/강화가 생겨도 적 사망이나 상점 코드에 예외를 추가할 필요가 없어야 한다.

## 5. 현재 확정된 데이터

신규 시작은 **0코인·0조각·초기 교리 지급 없음·장착 없음**이다. 초기값은 최초 프로필 생성 때만 적용한다. 저장 불러오기·씬 이동·사망에서 기존 자산을 초기화하지 않는다. 테스트에서 임의로 준비한 교리와 조각은 픽스처 데이터다.

드롭: 개 5~7, 신도 3~5, 간부 7~8, 보스 0코인. 지정 범위의 양 끝을 포함한 균등 정수 추첨이다.

플레이어 생존 중에는 교리·환경 피해 등 출처와 무관하게 처치 보상을 지급한다. 사망 확정 이후에는 사망 교리 효과로 처치한 적을 포함해 코인 처치 보상을 지급하지 않는다. 사망 전에 이미 접수한 대기 보상은 유지한다.

카드 가격은 일반 30, 고급 55, 희귀 95코인이다. 정확한 카드별 등급은 [상세기획 가격표](CurrencySystem_Design.md#3-교리-상점-가격과-등급)를 따른다.

상점 재고는 무제한이며 구매 후 같은 카드를 다시 살 수 있다. 한 장바구니에는 카드당 1장만 담는다.

보유·대기 코인 합계 상한은 999,999,999개이고, 조각은 종류당 9,999개다. 코인은 상한 이내 금액만 지급하고 초과분은 지급하지 않는다. 조각 한도를 초과하는 구매는 자산 변경 없이 실패한다.

연출 테스트 초기값은 퍼짐 0.2초, 비행 0.45~0.7초, 시차 0.03초, 동시 표시 64개다. 화면 밖 처치는 가장자리에서 HUD로 이동하며, 연출 수치는 테스트하면서 조정한다.

설정 에셋은 초기값·드롭·손실률·상한, 카탈로그는 가격·등급의 단일 출처로 둔다. 기존 HUD의 내장 예시 교리를 실제 소유·장착 데이터로 취급하지 않는다.

## 6. 사망·장착 처리에 연결할 때

반드시 다음 순서로 설계한다.

1. 사망을 확정하고 신규 처치 보상을 차단한 뒤, 기존 사망 교리 효과를 한 번 처리한다.
2. 교리를 전부 미장착 상태로 돌린다.
3. 효과·구독·버프·슬롯 연결을 정리한다.
4. **해제 후 보유 교리 조각 목록 전체**를 확정한다.
5. 조각 총수의 30%를 버림하여 개체별 무작위로 소실시킨다.
6. 비행 중 금액을 정산한 코인에도 30% 버림 손실을 적용하고 결과를 함께 저장한다.
7. 테스트 씬에서 잔액·잔여 조각·장착 없음·완료 이벤트를 확인한다.

기존 OnDeath를 다시 발행해 같은 사망 교리 효과를 두 번 실행하지 않는다. 효과 처리 후 전체 해제와 조각 손실 순서를 지킨다.

예: 미장착 7조각과 장착 교리 2개에 사용된 6조각은 해제 후 총 13조각이다. 무작위 3조각을 잃고 10조각이 남는다. 장착 교리 3개에 사용된 9조각만 있으면 2조각을 잃는다.

원본 조각은 해제 후 목록에 정확히 한 번만 포함한다. 이미 보유 목록에 들어 있는 조각을 해제했다고 다시 지급하지 않는다. 장착에 사용되어 가용 목록에서 제외됐던 조각은 어댑터가 해제 후 원본 보유 목록으로 정규화한다.

장착 교리 수로 손실을 따로 계산하거나 ‘미장착 완성 교리 보관함’을 추가하지 않는다. 모든 교리가 미장착된 상태에서 전체 조각 목록 하나로 처리한다. 처리 후 잔여 조각만 남고 장착은 비어 있어야 한다.

저장 실패/중복 사망에서는 해제 반환이나 소실을 반복하지 않는다. 최초 계획을 유지해 재시도하고, 일반 거래는 일관된 결과가 준비될 때까지 잠근다.

실제 재단·장착 시스템 구현은 이번 범위에 포함하지 않는다. 테스트 장착 어댑터로 위 순서를 검증한다. 실제 로비 복귀는 후속 메인 루프의 사망 완료 이벤트 수신자가 담당한다.

## 7. 저장과 향후 메인 루프 연동

이번 테스트 범위:

- 코인·조각·pending·거래 ID·사망 결과의 저장/복원.
- 비행 중 종료 후 보상 한 번 정산.
- 같은 처치/사망 ID 재요청의 중복 방지.
- 전체 해제 후 원본 조각 중복 추가 없음.
- 신규 프로필 0자산과 기존 저장 복원 구분.
- 정상본·백업 검증과 저장 실패 처리.
- 실제 사용자 저장을 수정하지 않는 격리된 테스트 파일 사용.

후속 메인 루프 연동:

- 위치·HP·적 생사·역할 수행 상태를 경제와 같은 시점으로 저장.
- 안정적인 스테이지 인스턴스/스폰 ID와 처치 보상 연결.
- 사망 결과 확정 후 실제 로비 전환.
- 재단의 장착/조각 연결과 전체 해제 어댑터 연결.
- 진행 중 스테이지 이어 하기와 엔딩 정책.

이번 테스트 통과를 실제 로비·이어 하기 연동 완료로 표시하지 않는다. 저장 스키마를 바꾸면 버전과 마이그레이션 계약을 갱신한다.

## 8. 현재 파일과 향후 수정 위치

예정 신규 경제 코드 위치는 Assets/Scripts/Economy/이며 아직 구현하지 않았다. 상세 책임·테스트 어댑터·범위는 [개발명세서](CurrencySystem_TechnicalSpec.md)를 따른다.

사망 효과와 처치 보상(P03), 상점 재고·반복 구매(P04), 드롭 분포·환경 처치 보상·상한과 초과분 처리는 사용자 제안 채택으로 모두 확정됐다. [상세기획 10장](CurrencySystem_Design.md#10-규칙-확정과-후속-검토)에 확정 상태, 연출 테스트 초기값, 후속 콘텐츠 결정 보류를 구분해 기록한다.

초기 지급 없음, 전체 미장착 후 단일 조각 목록에서 30% 손실, 테스트 씬 한정 검증, 메인 루프 후속 연동은 사용자 확정 사항이다. 이 항목들을 미결정으로 되돌리거나 작업 범위를 확대하지 않는다. **별도 지시 전에는 구현을 시작하지 않는다.**
