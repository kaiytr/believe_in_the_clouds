# 재화 시스템 개발 인수인계

작성일: 2026-10-31

**인수인계 시점: 게임 규칙과 문서 작성 완료, 재화 시스템 구현 전.** 현재 요청은 다른 로컬에서 이어가기 위한 준비다. 이 문서를 읽거나 파일을 이동하는 것만으로 구현을 시작하지 않는다. 사용자에게 별도 구현 지시를 받은 뒤 개발한다.

## 1. 먼저 읽을 문서

1. 이 인수인계 문서: 현재 상태, 이동 항목, 다음 작업.
2. [상세기획](CurrencySystem_Design.md): 확정 게임 규칙과 가격표. 게임 규칙의 기준 문서다.
3. [개발명세서](CurrencySystem_TechnicalSpec.md): 책임·API·저장·테스트 어댑터·구현 순서.
4. [개발자·AI 가이드](CurrencySystem_Guide.md): 공통 API 사용 계약과 확장 시 주의할 점.
5. [기존 StageTest 가이드](StageTestGuide.md): 이미 있는 전투 검증 씬과 조작법.

기획의 그림 원본은 [교리 상점 가격표](CurrencySystem_References/DoctrineShopPrices.png)에 있다. 임시 첨부파일 경로에 의존하지 않도록 프로젝트 안에 보관했다. 이 문서의 경로는 모두 프로젝트 기준이며 새 로컬의 절대 경로에 맞춰 접근한다.

| 항목 | 인수인계 시점 상태 |

| 공통 코인 지급·소비 API | 미구현. 문서의 클래스와 코드 예제는 향후 계약 |

| 드롭·자동 비행 | 미구현 |
| 코인·조각 저장과 사망 손실 | 미구현 |

이번 작업에서는 게임 코드·씬·프리팹·패키지를 변경하지 않았다. 문서 링크와 가격표 일치 여부를 확인했으며, Unity 컴파일이나 재화 동작 테스트가 통과한 상태로 인계하는 것은 아니다.

## 3. 이동 시점의 Git 기준

아래는 문서 커밋 전 확인한 작업 기준이다. 문서가 포함된 커밋은 이 기준 커밋 이후에 추가된다.

- 기준 브랜치: Puri
- 기준 커밋: d9d9c3176bcd140ef928fa3158f4278ea35da45d
- 커밋 제목: 보스 4타 연속 베기와 공격 선택 개선
- 커밋 전 README.md: 수정됨.
- 커밋 전 재화 문서·가격표 원본·인수인계 문서: 미추적 신규 파일.

이관 대상은 아래 여섯 파일을 함께 담은 문서 커밋이며, 전송 대상은 origin/Puri다. 새 로컬에서는 **해당 문서 커밋이 포함된 최신 Puri 브랜치**를 가져온 뒤 파일 목록을 확인한다. 위 기준 커밋만 checkout하면 이번 재화 문서는 포함되지 않는다. 원격을 사용할 수 없다면 아래 파일을 직접 복사하는 방법도 가능하다.

반드시 함께 옮길 재화 문서:

```text
README.md
Docs/CurrencySystem_Handoff.md
Docs/CurrencySystem_Design.md
Docs/CurrencySystem_TechnicalSpec.md
Docs/CurrencySystem_Guide.md
Docs/CurrencySystem_References/DoctrineShopPrices.png
```

이동 전에는 git status --short로 미추적 파일까지 확인한다. 일반 git diff만 확인하면 새 문서와 가격표가 검토 대상에서 빠질 수 있다. 새 로컬에서 같은 파일 목록과 내용을 다시 확인한다.

## 4. 새 로컬 환경 준비

프로젝트 자체를 새 로컬에서 사용할 수 있어야 한다. Git으로 프로젝트를 가져오거나 전체 소스 구조를 복사하고, 다음 항목을 포함한다.

- Assets 전체와 각 .meta: 씬·프리팹·스크립트·에셋 GUID 연결.
- Packages/manifest.json, Packages/packages-lock.json.
- ProjectSettings 전체.
- Docs, README 및 기존 루트 기획 문서.
- 저장소를 사용하는 경우 .gitignore와 필요한 Git 이력.

Library, Temp, Logs, obj와 IDE 생성 파일은 프로젝트 소스와 구분한다. 새 환경에서 생성할 캐시를 개발 인수인계 자료로 의존하지 않는다. 프로젝트의 .gitignore를 따른다.

프로젝트에 기록된 환경:

| 항목 | 버전/구성 |
| --- | --- |
| Unity | 6000.3.5f2, ProjectSettings/ProjectVersion.txt 기준 |
| Unity Test Framework | 1.6.0 |
| uGUI | 2.0.0 |
| Input System | 1.17.0 |
| URP | 17.3.0 |
| 런타임 asmdef | BelieveInTheClouds.Runtime |
| 테스트 asmdef | BelieveInTheClouds.EditModeTests, BelieveInTheClouds.PlayModeTests |

전체 패키지 기준은 manifest와 lock 파일이다. 환경 이동 과정에서 Unity·패키지 버전을 임의로 올리지 않는다. 새 환경의 사용자 경로를 코드·문서 예제에 하드코딩하지 않는다.

## 5. 확정 규칙 요약

세부 수치와 카드별 가격은 상세기획을 기준으로 한다. 다음 규칙은 다시 미결정으로 돌리지 않는다.

- 신규 시작: 0코인, 초기 교리·조각 지급 없음, 장착 없음.
- 드롭: 개 5~7, 신도 3~5, 간부 7~8, 보스 0. 양끝 포함 균등 정수 추첨.
- 생존 중 처치 보상: 플레이어 공격·교리·환경 피해 등 출처와 무관하게 지급.
- 사망: 기존 사망 교리 효과를 한 번 처리한 뒤 전부 미장착으로 돌린다. 사망 확정 이후 처치 보상은 없다.
- 조각 손실: 전체 해제 후 보유 조각 목록을 하나로 확정하고, 총수의 30%를 버림해 개체별 무작위로 소실한다.
- 코인 손실: 비행 중 대기 보상을 포함한 총액의 30%를 버림한다.
- 상점: 일반 30·고급 55·희귀 95코인. 무제한 재고, 장바구니 카드당 1장, 결제 후 반복 구매 가능.
- 한도: 보유·대기 코인 합계 999,999,999개, 조각 종류당 9,999개. 코인 초과분은 지급하지 않는다.
- 획득: 적 위치에서 퍼진 코인이 우측 하단 HUD로 비행하고 도착 시 잔액이 오른다. 접근·줍기 입력은 없다.
- 저장: 코인·조각·대기 보상·거래 ID·사망 결과를 일관되게 저장한다.
- 확장: 다른 기능도 공통 메서드로 지급·소비·조회할 수 있어야 한다.

손실 예: 미장착 7조각과 장착 교리 2개에 사용된 6조각이면, 전부 해제한 목록은 13조각이다. 3조각을 잃고 10조각이 남으며 장착은 비어 있다.

장착 교리 개수로 별도 손실을 계산하거나, ‘미장착 완성 교리 보관함’을 새 자산으로 추가하지 않는다. 해제 때 이미 소유한 조각이 중복 지급되지 않게 한다.

연출 초기값은 퍼짐 0.2초, 비행 0.45~0.7초, 시차 0.03초, 동시 표시 64개다. 시간·크기·색상·표시 수는 테스트로 조정한다. 엔딩 이후 자산 계승, 실제 스테이지 구성과 첫 구매 목표 시간은 후속 결정으로 보류한다.

## 6. 현재 작업 범위

목표는 **재화 시스템을 테스트 씬에서 독립 검증**하는 것이다.

포함: 공통 API, 경제 원장·저장, 기존 인벤토리 호환, 가격·결제, 드롭·비행·HUD, 테스트 장착 어댑터, 사망 전체 해제 후 손실, 자동 테스트와 화면 검증.

후속: 실제 로비·분기·스테이지 역할 진행·엔딩·재단 전체·실제 사망 로비 복귀·위치/HP/적 생사 전체 이어 하기. 이 기능들을 재화 테스트의 선행 조건으로 개발하지 않는다. 필요한 이벤트·스냅샷 계약과 테스트 어댑터만 둔다.

최종 목표인 진행 중 스테이지 이어 하기는 유지되지만 실제 메인 루프 연결은 나중 작업이다. 이번 테스트 통과를 전체 메인 루프나 이어 하기 완성으로 보고하지 않는다.

## 7. 구현 지시를 받은 뒤의 시작 지점

1. 새 로컬의 AGENTS.md 등 적용 지침과 실제 Git 상태, 문서 파일 목록을 확인한다.
2. 문서와 현재 코드가 같은 기준인지 확인한다. 차이가 있으면 기존 변경을 보존하며 확인된 차이를 기록한다.
3. EconomySettings·경제 프로필·저장소·원장·공통 API부터 구현한다.
4. DoctrineInventory와 ShopCatalog/ShopScreen/ShopCardView에 가격·결제를 연결한다.
5. EnemyUnit의 실제 사망, DoctrineHud의 재화 배지, CoinFlightView를 연결한다.
6. PlayerHealth 사망과 테스트 장착 어댑터를 통해 사망 효과 → 전체 해제 → 단일 조각 목록 손실을 연결한다.
7. 저장 실패·중복 거래·비행 중 사망/종료·상한을 자동 테스트하고 실제 화면을 확인한다.
8. 결과서에 구현 범위, 테스트 결과, 연출 조정값, 메인 루프 미연동 상태를 기록한다.

구체 API 계약과 검증 표는 개발명세서에 있다. 실제 구현 클래스 이름이 바뀌면 명세와 가이드 예제를 함께 갱신한다.

우선 볼 파일:

- Assets/Scripts/UI/DoctrineHud.cs
- Assets/Scripts/Shop/ShopScreen.cs, ShopCatalog.cs, ShopCardView.cs
- Assets/Scripts/Doctrine/DoctrineInventory.cs, DoctrineManager.cs
- Assets/Scripts/Enemy/Core/EnemyUnit.cs
- Assets/Scripts/Combat/PlayerHealth.cs
- Assets/Tests/EditMode, Assets/Tests/PlayMode
- Assets/Scenes/StageTest.unity, Assets/Scenes/ShopTest.unity

기존 HUD의 내장 예시 교리는 실제 초기 자산이 아니다. 실제 빈 상태 검증과 구분한다. 테스트 저장 파일은 사용자 프로필과 분리한다.

## 8. 새 로컬에서 이어받을 때 사용할 요청문

다음 요청문은 문서 인계와 상태 확인용이다. 이 요청만으로 구현을 승인하지 않는다.

```text
이 프로젝트의 재화 시스템 작업을 이어받아줘.
Docs/CurrencySystem_Handoff.md부터 읽고, 연결된 상세기획·개발명세서·개발 가이드를 확인해줘.
현재는 게임 규칙과 문서만 확정됐고 재화 시스템 구현은 시작하지 않은 상태야.
범위는 테스트 씬에서 재화 시스템을 독립 검증하는 것이며 메인 플레이 루프 연동은 나중이야.
사망 시에는 전부 미장착으로 돌린 뒤 전체 보유 조각 목록의 30%를 버림해 손실 처리해야 해.
새 로컬의 파일과 Git 상태를 확인하고, 실제 코드와 문서 간 차이만 보고해줘.
내가 별도로 구현을 시작하라고 하기 전에는 코드·씬·프리팹을 수정하지 마.
```
